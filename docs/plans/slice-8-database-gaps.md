# Slice 8 — verified database boundaries and next database-task contract

Historical pre-Slice-8B audit. The explicitly authorized [Slice 8B implementation](../../src/features/business-memory/SLICE_8B.md) now supplies scoped claim and atomic approval/writeback primitives. Verified C6/C7 authority is still unavailable. Proposed names below are retained as audit history; use the actual contracts in the new handoff.

Audit date: 4 November 2026, Asia/Jakarta. All five active migrations and their actual generated types were inspected. **No schema, migration, RLS, grants or RPC body was changed for Slice 8.** This document proposes follow-up capabilities; none of the proposed names below is an implemented RPC.

## Current operations

- `campaign_memories`: one row per `(business_id, source_evaluation_id, source_version)`, mutable draft content with existing `content_hash`; review states only `draft/approved`, embedding states only `queued/ready/failed/stale`. There is no row revision or candidate revision-history table. Owner review/rejection is bounded application audit metadata in `lessons_json`, not another database lifecycle state.
- A complete candidate is a single INSERT with source/interpretation/audit JSON. Composite foreign keys, unique source identity and a stable request UUID protect scope and duplicates. Draft review is a single UPDATE filtered by owner/business, draft status and the expected existing content hash. It changes the hash and stores actor/time/request/expected hash. These operations do not claim atomic approval/source CAS.
- `approve_campaign_memory(business, memory, content_hash, model, profile, actor)`: locks memory, checks owner/hash and final evaluation kind, then atomically marks approved and enqueues a deduplicated `embed_memory` job. It **does not validate latest evaluation, completed lifecycle, current source revisions, owner-review JSON, current C7 eligibility, or atomically invalidate older canonical sources**.
- `claim_jobs(limit, lease_seconds, max_attempts)`: global service-only SKIP LOCKED claim for **all job types and businesses**. No job-type/business/job-ID selector is available. A memory-only owner runner cannot safely claim through it on the shared application queue without taking payment/email/other jobs.
- `complete_memory_indexing(memory, hash, embedding_version, model, profile, vector)`: validates nonzero vector dimension and expected approved memory key; writes vector/ready idempotently. It has no job ID, lease or attempt argument. `finish_job` separately fences acknowledgement by attempt/lease. A worker may safely reconcile an already ready same-key result, but this is not atomic lease-fenced vector+job completion.
- `match_campaign_memories(business, vector, model, profile, embedding_version, limit, min_similarity)`: owner checked SECURITY INVOKER. SQL materializes tenant+approved+ready+compatible profile/version **before** distance ranking/limit. It does not attest C7 source eligibility/freshness. Application retrieval therefore requires a trusted attestation port for any purported verified row; absent that authority it reports unavailable instead of trusting JSON flags.

## Synthetic restriction remains mandatory

`20261104092000_reject_synthetic_finalization_memory_approval.sql` rejects approved memory sourced from `metrics_json.finalization.mode=development_synthetic`, including direct privileged writes. Current C7 handoff always excludes synthetic sources from production. Source campaigns from Slice 7B can produce local **draft** candidates and reviewed/rejected draft audit only. Current server approval fails closed; no synthetic override, alternative approval route or production fallback was added.

The application checks actual completed campaign state/version/timestamp, latest reviewed final evaluation, C7 hash and source bindings before generating. A changed preorder revision can make a dated draft stale. The draft remains readable; source checks before INSERT/review are preflight and cannot become a claim of atomic source approval.

## Separate task required before enabling the blocked path

1. **Verified C7 authority:** integrate the real final-evaluation/completeness/provenance contract after C1/C6/C8. The current `evaluationHandoff()` deliberately returns `productionEligible=false`. Do not change that merely for a demo. Its attestation must bind the immutable latest reviewed final evaluation and sealed campaign to the memory source/content/version.
2. **Atomic approval/source validation** (proposed `approve_campaign_memory_candidate` or reviewed extension of the existing RPC): accept owner/business, memory ID, expected content hash, exact source evaluation/campaign revision and compatible embedding configuration. Under a consistent campaign→memory lock order, recheck source eligibility/completeness/provenance/review/latest identity, then approve+dedupe enqueue in one transaction. Preserve the synthetic guard and existing grants. Decide any old-source stale propagation before rollout.
3. **Scoped claim** (proposed `claim_memory_jobs`): trusted server only, verified business scope, only `job_type=embed_memory`, bounded batch/lease/retry count, SKIP LOCKED. Alternatively provide a real shared job dispatcher with handlers for every claimed type; this task does not implement other members' handlers.
4. **Lease-fenced writeback** (proposed `complete_memory_index_job`): expected job ID+attempt/lease and memory key/profile/source/version in one transaction. Verify job/memory/business association, persist a valid vector and acknowledge the job atomically; replay the exact durable key safely. Provider calls stay outside SQL transactions.
5. **Draft revision/correction policy:** the current unique source tuple is canonical, not a revision history. Do not increment `source_version` to fabricate a new evaluation version. Specify a genuine source/candidate revision contract and post-completion correction lifecycle if text revisions/history are required. This slice supports current review/rejection audit, not immutable candidate-text revisions.

These are reviewable requirements, not permission to modify SQL. AGENTS.md §4 and the Slice 8 prompt require a separately authorized database task.

## What has been verified without a bypass

Actual local GoTrue/JWT/RLS, single-document draft persistence, canonical duplicate reconciliation, hash-CAS review, source-stale rejection, direct SQL synthetic approval rejection, zero new indexing jobs for these drafts, and honest cold-start/unavailable states are tested on the active local stack.

Worker processing, embedding contracts and positive historical grounding are tested with explicitly hypothetical port fixtures. Pgvector/indexing/job RPC tests use a **labelled disposable PostgreSQL container and separate `memory_review` database**. It reuses the existing legacy sandbox SQL fixture after retaining every original pgTAP assertion; added records explicitly say synthetic/test-only/not production eligible. Draft→approval uses the real legacy RPC and its limitations, never a direct fake approved production insert. This is lower-level SQL plumbing evidence; it does not make the legacy fixture an eligible Slice 7B completed source and does not prove production approval or semantic relevance. No fixture is copied to the active application database.
